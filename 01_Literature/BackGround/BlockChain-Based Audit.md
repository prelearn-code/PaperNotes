# 完整性审计研究背景

## 1. 研究问题与现实背景

云计算、边缘计算和去中心化存储将数据交由用户难以完全控制的云服务商、边缘节点或分布式节点保存。数据拥有者无法通过本地文件比较持续确认远端数据是否完整，存储服务商也可能因硬件故障、软件错误、节点退出、空间优化或恶意行为而删除、篡改或丢失数据。若每次验证都下载整个文件，通信和计算开销又会抵消外包存储的价值。

完整性审计的目标是在不下载完整数据的条件下，以较小的挑战、响应和验证成本确认远端数据仍然存在、未被篡改、属于正确版本，并在多节点环境下定位失责主体。典型安全目标包括：

- **可验证持有性**：服务器确实保存了足以恢复或重构数据的内容。
- **完整性与不可伪造性**：服务器不能在缺少原始数据时生成可通过验证的证明。
- **公开可审计性**：第三方能够代替数据拥有者发起挑战和验证。
- **隐私保护**：审计过程不泄露原始数据、访问模式、用户身份和共享关系。
- **动态适应性**：插入、删除、修改和追加后仍能低成本更新认证元数据。
- **责任可追溯性**：能够把错误证明绑定到具体服务商、存储副本或审计节点。

Zotero 文献中的研究表明，完整性审计已经从静态云文件的持有性验证，逐步扩展到动态数据、多副本、共享与去重、区块链责任记录、可搜索加密、后量子密码、边缘设备和可信执行环境等方向。

## 2. 数据持有性证明与公开审计基础

### 2.1 PDP/PoR 范式

Ateniese 等人的 *Provable Data Possession at Untrusted Stores*（2007，Zotero：`storage/THVYMYSN`）是外包存储审计的重要奠基工作。方案预先为文件块生成认证标签；审计时，验证者随机选择数据位置和系数，服务器返回被挑战数据块的线性组合及聚合标签，验证者通过同态认证关系或配对等式判断服务器是否仍掌握足够的数据。

这种设计以抽样审计和同态聚合降低通信成本：一次挑战能够覆盖多个数据块，证明大小主要与挑战规模相关，而不是与文件总大小线性相关。PDP 主要强调服务器对数据的可验证持有；PoR 则进一步要求数据可恢复，通常结合纠删码、冗余编码或可提取性证明。

### 2.2 从私有验证到公开审计

早期方案通常由数据拥有者持有秘密密钥并执行验证。随着云存储规模扩大，研究转向第三方审计者（TPA）和公开验证，使用户不必长期在线。但 TPA 也成为新的信任边界：TPA 可能与云服务器串通、从响应中推断数据，或者伪造审计结果。因此，公开审计方案通常还需要审计者隐私、不可抵赖日志和零知识式证明。

PDP/PoR 的抽样性质决定了其不是逐比特的连续监控。挑战规模过小可能漏检少量损坏，挑战过密又会增加服务端和验证端开销；传统模型还常把文件看作静态对象，把服务器看作单一主体，难以覆盖多副本、去重、检索和跨组织共享。

## 3. 动态数据与多副本审计

### 3.1 动态数据

数据库、日志、模型参数和协作文件会持续插入、删除、修改或追加。若每次更新都重新生成整个文件的认证标签，方案不可扩展；若只更新局部标签，则必须防止旧证明重放、版本混淆和恶意删除。

Liu 等人的 *MuR-DPA: Top-down Levelled Multi-replica Merkle Hash Tree Based Secure Public Auditing for Dynamic Big Data*（2014，Zotero：`storage/35FPPELG`）将 Merkle 哈希树的结构化认证与多副本审计结合，通过树路径证明绑定数据块位置、文件结构和版本，更新时只需维护受影响路径。动态审计的关键问题包括更新顺序和版本号、旧版本证明防重放、批量更新、树重构和元数据热点。

### 3.2 多副本真实性

同一文件通常保存多个副本，以提高可用性和容错性。但证明某个数据值存在，并不等于所有声明副本都真实存在。恶意服务商可能只保存一份副本，却通过重复响应伪装成多份。因此，多副本审计必须让每个副本具有可区分的身份、位置或随机化标签，并把证明绑定到具体存储节点。

Zhang 等人的 *Efficient Blockchain-Based Data Integrity Auditing for Multi-Copy in Decentralized Storage*（2023，Zotero：`storage/9X2LRAZC`）体现了副本身份绑定、节点责任定位和批量挑战的研究趋势。副本越多，安全性和可用性越强，但标签、挑战、验证和修复成本也随之增加。

## 4. 区块链去中心化审计

### 4.1 引入区块链的动因

传统公开审计依赖 TPA，存在集中化信任、审计日志可被修改以及争议证据不足的问题。区块链通过分布式账本、智能合约和共识机制记录数据承诺、挑战、响应摘要、验证结果和处罚规则，使审计过程具备公开见证和不可篡改的时间顺序。

Tian 等人的 *Blockchain-Based Secure Deduplication and Shared Auditing in Decentralized Storage*（2022，Zotero：`storage/ES7WJ97R`）、*Enabling Secure and Efficient Decentralized Storage Auditing With Blockchain*（`storage/P78INI46`）、Zhang 等人的多副本区块链审计论文，以及 Miao 等人的 *Blockchain-Based Shared Data Integrity Auditing and Deduplication*（2024，`storage/BV59MXAT`）共同体现了这一方向。

区块链通常不直接保存大文件，而保存文件摘要、标签承诺、用户授权集合、挑战随机数、证明摘要和审计状态。大数据仍位于链下，链上负责公共见证、流程自动化和争议记录。因此，区块链审计并不是把文件放到链上，而是把“数据状态、审计流程和责任证据”组织成可验证的责任链。

### 4.2 共享数据、去重与区块链审计

共享数据环境中，多个用户可能访问同一文件。逐用户上传和生成标签会造成重复存储，直接共享密钥又会带来越权、用户撤销和所有权证明问题。Miao 等人（2024）的工作把收敛加密、去重所有权证明、身份基广播加密（IBBE）和区块链审计结合起来：相同文件可以复用存储内容，授权用户集合通过 IBBE 表达，去重用户需要证明其确实拥有文件，区块链记录挑战与审计流程。

此时审计对象已不只是文件块，还包括认证标签、授权集合、密钥封装和所有权证明。审计正确性不仅意味着数据未被篡改，还意味着访问者被正确授权、撤销用户失去访问能力、去重节点确实保存了承诺数据，并且链上状态与链下数据保持一致。

### 4.3 区块链方案的限制

区块链不会自动消除信任和性能问题。链上交易与智能合约执行会产生成本，频繁审计可能造成吞吐瓶颈，共识延迟也可能不适合实时业务。链上摘要不可篡改并不等于链下数据可恢复；主节点、预言机、合约管理员和数据修复节点仍可能构成新的信任中心。

公开账本还可能泄露挑战时间、审计频率、文件版本、共享关系和节点异常记录。因此，区块链应被视为责任与证据层，而不是独立的完整性算法，需要与隐私保护、匿名凭证、零知识证明、链下存储和故障恢复机制结合。

## 5. 隐私保护、匿名与访问控制

审计证明可能包含数据块线性组合、标签、挑战位置和访问时间。若验证过程处理不当，TPA 或其他观察者可能根据多次响应推断原始数据、文件特征、访问模式或用户关系。Ding 等人的 *Towards Fully Anonymous Integrity Checking and Reliability Authentication for Cloud Data Sharing*（2023，Zotero：`storage/WT9AWNWR`）将匿名认证、完整性检查和可靠性认证结合，反映了从“证明服务器有数据”到“在不暴露用户身份的情况下证明数据可靠”的转变。

共享和去重场景还面临所有权确认攻击：攻击者上传猜测文件，根据系统是否判定重复推断受害者是否拥有该文件。Zhang 等人的 *Blockchain-Based Privacy-Preserving Deduplication and Integrity Auditing in Cloud Storage*（2025，`storage/HBTPCB64`）和 Liu 等人的 *Blockchain-Assisted Fine-Grained Deduplication and Integrity Auditing for Outsourced Large-Scale Data*（2025，`storage/99KVTL89`）代表了隐私保护去重、细粒度授权和完整性审计联合设计的趋势。

群签名、环签名、身份基签名、匿名凭证、盲化指纹、服务器辅助所有权证明和零知识证明可用于降低身份或内容泄露，但它们会增加密钥管理、交互次数和验证成本。完整性也不能等同于可授权性：文件在比特层面完整，并不意味着未授权用户不能读取，或者被撤销用户已经失去访问能力。

## 6. 可搜索加密与结果完整性

在加密云存储中，服务器不能直接读取明文，但用户仍希望按关键词、范围或相似度检索。传统完整性审计只能证明底层密文文件被保存，不能证明服务器返回了完整、正确且新鲜的查询结果。服务器可能遗漏结果、加入无关结果、使用旧索引，或通过搜索过程泄露关键词和访问模式。

Song 等人的 *Enabling Verifiable Search and Integrity Auditing in Encrypted Decentralized Storage Using One Proof*（2025，Zotero：`storage/IYCEPFD3`）把可验证检索和完整性审计结合为一个证明，目标是同时确认搜索结果、底层数据完整性和结果版本。Miao 等人的 *Blockchain-Assisted Searchable Integrity Auditing for Large-Scale Similarity Data With Arbitration*（2025，`storage/3K6UCBDT`）进一步关注大规模相似数据、搜索审计和区块链仲裁。

可搜索审计至少需要验证四类属性：

1. **完备性**：所有满足查询条件的结果都被返回。
2. **正确性**：返回结果确实满足关键词、范围或相似度条件。
3. **新鲜性**：结果来自最新授权版本，而不是旧索引或过期快照。
4. **隐私性**：证明不泄露查询关键词、未命中文档和完整访问模式。

因此，证明结构由数据块线性组合扩展为索引承诺、集合成员/非成员证明、排序或相似度证明以及版本承诺。真正困难的不是证明单个结果属于集合，而是低成本证明结果全集完整，并同时绑定动态版本和访问权限。

## 7. 格基与后量子完整性审计

大量传统审计方案依赖 RSA、离散对数、双线性配对或椭圆曲线。若大规模量子计算机实现 Shor 算法，这些基础将面临系统性风险。Zhang 等人的 *Identity-based key-exposure resilient cloud storage public auditing scheme from lattices*（2019，`storage/CLGGYLMK`）、Cheeturi 等人的 *Lattice-Based Efficient Certificateless Public Auditing Scheme from RLWE for Cloud Storage*（2024，`storage/JK9G7Q8N`）和 *Lattice-Based Public Auditing Schemes for Cloud Storage Security: A Comprehensive Survey*（2026，`storage/2KZI2SFC`）体现了格基公开审计路线。

LWE、Ring-LWE、短向量困难问题和格基签名可以支持身份绑定、密钥暴露抵抗、无证书公钥、承诺和批量验证。代价是格基密钥、签名和证明通常更大，矩阵或多项式运算会增加通信、计算和能耗。对移动和边缘设备而言，后量子审计还必须评价标签大小、更新频率、端侧峰值内存、批量验证和网络开销，不能只进行底层签名替换。

## 8. 边缘计算、轻量化与 TEE

物联网、移动终端和边缘节点资源有限，难以承担大规模标签生成和频繁验证。Xu 等人的 *MPA: Lightweight and Updatable Integrity Auditing for Decentralized Storage Using Merkle Trees and Polynomial ...*（2026，`storage/CSH3HBNA`）以及 Tang 等人的 *MIDAS Load-Balanced Metadata-Outsourcing ID-Embedded Data Auditing Scheme for Mobile Devices*（2026，`storage/DG2TD8PZ`）代表了轻量化、负载均衡和元数据外包方向。

相关研究通常通过 Merkle 树、聚合签名或多项式承诺压缩认证元数据，将标签生成、证明聚合和部分验证转移给边缘节点或辅助服务器。元数据外包可以减轻端侧负担，但辅助节点若篡改或删除标签、索引、版本树和副本状态，会导致正确数据无法验证；元数据更新还可能暴露访问模式。因此，评价轻量化方案时，应同时关注端侧能耗、峰值内存、在线时长、网络交互次数和故障迁移能力。

Zhang 等人的 *Anonymous Integrity Auditing Scheme Based on Trusted Execution Environment for Distributed Edge Computing*（2026，`storage/58P2TU8Y`）将 TEE 引入分布式边缘审计。TEE 能通过硬件隔离、远程证明和受保护内存让审计程序、密钥和标签在隔离空间运行，减少部分零知识证明的计算负担。但它仍面临侧信道、回滚攻击、固件漏洞、供应链风险和远程证明依赖。必须明确 TEE 证明的是代码正确执行，还是代码使用了正确且最新的数据；可信硬件仍需与版本承诺、区块链日志和可恢复存储联合使用。

## 9. 研究演进与主要空白

完整性审计的研究演进可以概括为：

1. **静态持有性证明**：通过 PDP/PoR 和同态标签，以抽样证明代替完整下载。
2. **公开审计**：引入 TPA，降低用户在线负担，同时解决审计者隐私和串通问题。
3. **动态与多副本审计**：使用 Merkle 树、版本结构和副本绑定处理更新、删除、追加和副本真实性。
4. **共享与去重审计**：把所有权证明、收敛加密、授权集合、用户撤销和审计联合起来。
5. **区块链辅助审计**：将挑战、证明摘要、节点状态和争议处理写入可验证账本。
6. **可搜索完整性审计**：从证明文件保存扩展到证明查询结果的正确性、完备性和新鲜性。
7. **后量子与轻量化审计**：采用格基密码、聚合承诺、元数据外包和边缘协作适应长期归档和资源受限设备。

当前主要研究空白包括：

- **联合状态审计不足**：许多方案只证明数据块和标签，未同时证明索引、授权、版本、副本和恢复状态。
- **新鲜性和版本一致性不足**：服务器可能返回历史上正确但当前过期的证明，缓存和边缘副本会放大风险。
- **多副本责任绑定不足**：证明某个副本存在不等于每个承诺节点都保存独立副本，仍需支持失责定位和修复。
- **可搜索审计完备性成本高**：成员证明相对容易，结果全集完备性、排序正确性、相似度正确性和查询隐私更难。
- **隐私与公开仲裁存在张力**：链上记录便于争议处理，但也可能长期暴露审计频率、文件关系和用户行为。
- **评价指标不统一**：应同时评估初始化、单次与批量审计、动态更新、证明刷新、节点失效、仲裁、能耗和隐私泄露面。

## 10. 研究背景小结

完整性审计已经从单一云服务器上的静态数据持有性验证，发展为面向云边端和去中心化存储的综合可信性证明问题。研究对象由文件块扩展到副本、索引、授权、密钥、版本、查询结果和审计日志；信任主体由数据拥有者与 TPA 扩展到云服务商、边缘节点、区块链节点、智能合约、TEE 和多用户群体。

下一阶段有价值的问题不是简单叠加“区块链、去重、格基和审计”等关键词，而是在动态、共享、去重和可搜索的去中心化存储中，用一次或少量聚合证明同时确认数据内容、版本新鲜性、索引结果、副本责任和授权状态，并将隐私泄露、审计成本和故障恢复纳入统一评价。
