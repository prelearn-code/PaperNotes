# 相似去重完整性审计：后续研究实施路线与验收清单

日期：2026-09-09。

设计依据：[核心方案2.md](./核心方案2.md)。研究判断依据：[文献对标与创新点强化报告](./二区目标_文献对标与创新点强化_2026-09-09.md)。本文件是后续实施计划；文中拟建目录、算法、定理、实验和进度均不代表已经完成。

## 1. 先确定最终要交付什么

建议保持主题：**有限公共状态和审计预算下，相似去重对象的业务恢复保障。** 后续工作不再增加主贡献，而是将现有三项贡献分别做成可证明、可执行、可测量的结果。

| 主贡献 | 最终交付物 | 目前最主要缺口 |
|---|---|---|
| 业务恢复损失驱动的预算约束依赖审计 | 损失模型、检测界、预算配置算法、同预算比较 | 已有闭包与简化概率关系，尚无实际 PoR 强度下的完整配置算法和强基线收益证据 |
| 有限公共状态下的可启动元数据 | 启动模型、具体目录构造、成本分析、配置规则 | 当前分页构造尚未充分比较递归目录和动态 PoR，也未落实全部真实字节成本 |
| 可启动依赖对象的安全组合与实例 | 底层 adapter、安全游戏与组合证明、更新协议、可复现实验 | 尚未完成可执行实例及从底层提取合同到当前对象恢复的完整论证 |

面向较强期刊，目标是形成“一个中心技术结果＋两个紧密支撑结果”，而不是要求每项都发明一个密码原语。最终创新力度由证明和实验决定，文档改写不能替代它们。

### 1.1 近期必须完成与暂缓事项

**近期必须完成：** 固定研究边界；强基线；成本模型；挑战参数配置；一个 PoR adapter；认证目录；固定快照组合证明；更新及故障恢复实验。

**暂缓：** 通用 suite 注册、跨链、多级治理、多种底层密码方案、任意复杂恢复图、在线代表学习、全套经济激励。阈值信标、BFT、区块链记录和无放回 coverage 放在核心结果之后评估。

暂缓不等于删除现有设计。当前文档中的 BFT/信标属于部署候选，首个核心原型可使用具有明确假设的可信当前根发布者和交互随机挑战；两种信任配置必须分开标注，不能以简化原型的实验宣称已验证去中心化系统。

## 2. 总体顺序与四个决策关口

建议按照以下依赖顺序推进：

```text
明确主张、对象和成本口径
          ↓
强基线＋小规模精确分析 ──→ G1：是否还有可验证的增量？
          ↓
底层 PoR 微基准＋预算配置＋元数据配置
          ↓
固定快照协议与证明 ─────→ G2：接口与提取前提能否闭合？
          ↓
局部更新＋完整原型＋故障恢复
          ↓
成组实验与消融 ─────────→ G3：理论收益是否在实际成本下成立？
          ↓
全文重写、复现检查 ─────→ G4：所有主张是否都有证据？
```

| 关口 | 通过条件 | 不通过时的处理 |
|---|---|---|
| G1 创新可行性 | 强基线比较后仍有清晰、非人为制造的保证或成本增量 | 收紧贡献或调整构造；不能通过删掉强基线挽救结论 |
| G2 安全闭合 | 每个验证输入有来源；底层挑战、版本、提取权限与定理匹配 | 先限定固定快照、交互挑战；未证明的非交互或自适应扩展暂不进入主定理 |
| G3 实际收益 | 完整成本口径下，存在有解释、可重复的适用区域；边界场景亦报告 | 判断是否是实现问题、参数问题或方案本身无增量；如实调整定位 |
| G4 投稿完整性 | 摘要、贡献、算法、证明和实验彼此对应，没有以计划充当结果 | 继续补证据，或删除未兑现主张，不能只修改措辞掩盖缺项 |

## 3. 阶段零：冻结研究边界与主张账本

### 3.1 写出一页研究合同

首先新建 `research/spec_scope.md`，逐项固定以下内容。目录与文件名为建议，不要求立即创建空文件。

| 项目 | 第一版建议 | 必须解释的限制 |
|---|---|---|
| 对象 | 微批次归档；单代表 REP＋DELTA＋FALLBACK | 不外推到任意多代表依赖图或高频无限流 |
| 形成端 | 可信 Gateway 复核精确重构、加密和签名 | 公共审计不证明隐藏明文的分类质量 |
| 存储端 | 单恶意 CSP，可保留全部旧数据和标签 | 对外部即时取回能力的限制须由模型明确，不可暗中假设 |

## 4. 阶段一：建立公平强基线，先验证研究空间

### 4.1 审计策略基线

| ID | 基线 | 具体要求 |
|---|---|---|
| A0 | 完整对象序列化＋PoR | 包含全部恢复模板和映射，认证版本；不能故意漏掉元数据 |
| A1 | 均匀条带审计＋认证目录 | 使用相同表示和底层参数，完整计入目录可用性保护 |
| A2 | 固定 REP 审计＋普通抽样＋认证目录 | 允许对 REP 单独配置挑战强度，是必须击败或解释的关键基线 |
| A3 | 抽记录、展开依赖闭包、共享组件只证明一次 | 当前基础方案，先不加入新优化 |
| A4 | 预算配置后的闭包审计 | 同预算下联合选择 r 和各类组件挑战强度，是待研究方案 |

均匀条带审计仅作为理解差异的基线，不能用它替代 A2。还需区分均匀抽“条带”和均匀抽“编码块”，两者故障命中分布不同。

### 4.2 元数据布局基线

| ID | 布局 | 公平实现要求 |
|---|---|---|
| M0 | 公共全目录 | 统计单验证者持久状态和复制总量；在线本地读不虚增通信 |
| M1 | 单层外包元数据 | 允许条目 opening；不能要求每次全量下载 |
| M2 | 公开页描述符＋分页元数据 | 当前设计；公开目录本身及其访问证明也计费 |
| M3 | 仅公开根状态的递归目录 | 父页提供子页验证状态；统计逐层访问、证明和更新 |
| M4 | 动态 PoR 元数据对照 | 与静态页重处理方案分列；先做有来源的成本分析，再判断能否公平实现 |

M4 不一定要与每种策略做笛卡尔积组合。它首先用于检验“单层必然全量重处理”的论据是否成立。若只能取得解析成本或文献结果，应清楚标记，不混画成同机实测。

### 4.4 本阶段交付与验收

交付：基线规范、统一成本表、小对象精确计算程序、初步比较图。此阶段可以不实现全部密码运算，但所有成本估算必须标注来源和未测项。

验收：先展示一个 A2 相当或更好的场景，确认比较没有偏袒本方案；再寻找本方案具有实际增量的区域。若找不到，暂停扩展实现，先调整第一项贡献定位。

## 5. 阶段二：把第一项贡献做成算法与检测结果

### 5.1 分开定义三类故障

1. **规定路径不可恢复组件。** 删除或损坏超过恢复条件，组件无法按声明方法恢复，用于定义业务损失。
2. **可纠正的局部损坏。** 审计可能发现，但组件和业务记录仍可恢复，不应全部计为记录损失。
3. **任意恶意响应者。** 可选择性响应、伪造或拒绝服务，用于密码学安全游戏；不能用随机删块模型代替。

这三类实验和结论分别报告。固定失效模型便于推导和配置，恶意响应者模型用于证明安全，二者可以相互关联但不能混为一谈。

### 5.2 固定损失指标

设当前对象含 n 条记录，D⁺(ℓ) 包含记录恢复所需业务组件及验证元数据。对规定路径不可恢复组件集合 S，定义

\[
L(S)=|\{\ell:D^+(\ell)\cap S\neq\varnothing\}|.
\]

若只统计业务数据失效，应单独定义 Ldata，并与包含元数据的 L 区分。所有依赖计数都从认证映射推导，不能采信 CSP 自报的影响范围。

元数据拒绝返回导致目标无法解析时，审计应拒绝或按明确超时规则失败，不能跳过该记录再抽一条。此时“检测到服务失败”与“已证明业务内容不可恢复”仍需区分。

### 5.3 明确配置变量与目标

第一版保持有限候选集合，建议

\[
\theta=(r,c_{rep},c_{meta},c_{page},c_{ordinary},b),
\]

其中 r 为记录抽样数，c 为各类组件的底层挑战块数，b 为元数据页容量。预算先固定，随机数后产生。第一项算法先固定 b，第二项再枚举 b，避免一开始引入不可控的通用联合优化。

定义声明攻击集合 𝒮 和损失阈值 λ，目标为

\[
\min_{\theta\in\Theta(B_{proof},B_{read},b)}
\max_{S\in\mathcal S:L(S)\ge\lambda n}
P_{miss}(S;\theta).
\]

候选配置必须满足每次挑战的资源上界，不允许以抽到大闭包后重新抽样实现预算。对于当前单代表结构，可以先使用已有闭包目标数上界保守筛选，再研究更紧的可证明成本界。

### 5.4 先完成三个可核查推导

**推导一：理想命中模型。** 坏组件一旦被抽中必然拒绝，记录有放回均匀抽样时，漏检率为 `(1-L/n)^r`。仅作为理想参照。

**推导二：共享代表检测饱和。** 只有 REP 失效且影响 L 条记录，REP 被包含时拒绝概率为 αrep，整个闭包只验证 REP 一次，则

\[
P_{detect}=\alpha_{rep}[1-(1-L/n)^r].
\]

此式揭示 r 与 REP 挑战强度应联合选择，但不单独包装为重大理论突破。

**推导三：多个共享目标。** 对固定抽样结果 Q，令 A(Q) 为去重后的被审计组件集合。只有在条件化后每个组件挑战独立、故障固定且 αv 定义一致时，才能使用

\[
P_{miss}=\mathbb E_Q\prod_{v\in A(Q)\cap S}(1-\alpha_v).
\]

不满足独立条件时，改用联合分布或有效界；不能将共享证明误算为多次独立检测。若闭包解析阶段可能失败，应在模型中单独计入这一拒绝事件。

### 5.5 算法实施顺序

```text
输入：认证对象统计、固定页布局、预算、参数候选集合、声明攻击集合
1. 枚举候选挑战配置。
2. 以规范序列化和最坏闭包上界排除超预算配置。
3. 对小对象精确枚举抽样/故障状态，计算漏检率。
4. 对较大对象使用已证明的简化式或界；模拟结果单独标记。
5. 按最坏情形漏检目标选择配置，以确定性规则处理并列。
6. 在新的对象/故障实例上评估，并与 A2 的独立调参结果比较。
输出：配置、适用前提、目标值或界、完整成本、不可行时的原因。
```

穷举程序的价值是建立可信参照。只有证明搜索结构、获得可扩展算法或形成有意义的保证时，才考虑更强算法贡献。启发式可以作为工程方法，但需要报告它相对小规模精确最优的差距。

### 5.6 验收与停止条件

- 在小对象上解析结果与精确枚举一致；模拟在声明不确定性内吻合。
- 对没有 DELTA、REP 影响全部记录、仅 META 失效、预算不可行等边界有明确处理。
- 优化器不使用实际未公开的损坏位置；对比策略各自获得公平调参机会。
- 明确最优范围是有限参数/攻击集合，不能写“对所有攻击全局最优”。
- 若 A4 相对 A2 的收益仅来自额外预算或免费元数据，结果无效，重新设计比较。

## 6. 阶段三：把第二项贡献做成启动条件与配置规则

### 6.1 写出元数据依赖清单

为每种组件填写：验证需要哪些输入、这些输入放在哪里、如何认证、如何在丢失时提取、哪些输入必须公共可用。

| 组件 | 需要填清的内容 |
|---|---|
| REP/普通条带 | file id、版本、编码参数、标签或承诺参数、根、长度 |
| 元数据页 | 页描述符、范围、条目根、页 PoR 状态、子项完整性条件 |
| META | 固定公共入口、模板/恢复材料归属、解析规则 |
| 认证映射 | 成员证明之外的数量、覆盖、唯一性、顺序及版本关系 |

文件建议：`research/metadata_dependencies.md`。该表不完整时，不开始写组合提取定理。

### 6.2 分开两种启动任务

**在线启动：** 从公共当前根出发，获得本轮抽中记录的验证输入。CSP 正常提供认证 opening 可以完成解析，随后按协议审计相关元数据；隐藏或错误输入导致失败。

**恢复启动：** 当某些输入不再能直接下载时，按照合法依赖顺序调用满足前提的 extractor，逐步恢复其他组件的验证状态。认证正确不等于可提取；各必要页面仍需满足底层提取条件。

分别记录可访问闭包与可提取闭包。不能用“正常情况下能下载”证明恶意情况下可恢复，也不能要求所有正常审计都运行完整 extractor。

### 6.3 实现四种目录的最小版本

先固定条目长度和单一页容量，不立即加入冷热分层、可变容量或自适应重排。M0—M3 使用相同条目语义、底层参数和更新序列。

对 M3 根状态递归目录，必须有公开可用的根页验证状态，父页包含可认证的子页状态；每层范围与完整枚举规则明确，禁止重复子页、范围重叠和遗漏。它是正面比较对象，不能故意省略必要认证使其显得不安全。

### 6.4 完成限定模型下的成本分析

设 N 个条目、每项 a 字节、每页 b 项、页描述符 d 字节。对于当前公开页描述符分页，先分析

\[
S_{pub}(b)\approx\lceil N/b\rceil d+S_0,
\qquad U_{page}(b)=\Theta(ba).
\]

前提为定长条目、定长描述符、静态页重处理；随后用真实序列化替换估计。记录未满页、分裂、树路径、批更新和 d 随参数变化的影响。

公共根很小不等于验证者总状态很小；公开 PageDesc 放到远程公共服务时，也要统计其可用性假设、服务端持久量和轻客户端获取成本。单节点持久量与全体副本总量分别报告。

不要预设分页一定缩短完整证明。目录路径和页内路径相加可能仍为 O(log N)。新结果应落在实际状态预算、启动层数、更新代价或整体 Pareto 区域，而非只计算其中一段路径。

### 6.5 页容量选择规则

对每个候选 b：计算真实公共状态，调用阶段二的可行审计配置程序，加入更新负载对应的重处理成本，形成可行配置表。

若只给出多目标前沿，就报告非支配配置和选取理由；若需要自动选一个配置，事先固定目标优先级，例如“满足公共与读取预算后，先最小化最坏漏检，再最小化更新成本”。不能看完结果后更换目标以偏向本方案。

### 6.6 验收与停止条件

- 全部验证输入均有认证与可用性来源，公共入口能够启动声明的恢复过程。
- 四种目录的成本来自同一口径，冷启动与热缓存分别比较。
- 实际更新字节与理论量级一致，分裂等例外有单列结果。
- 若递归目录全面更优，应采用它或改变贡献定位；不能坚持分页名义而删掉对照。
- 如无法证明通用下界，明确给出构造成本和适用区间，不使用“最优”“不可避免”等过强措辞。

## 7. 阶段四：固定 PoR adapter，补齐安全论证

### 7.1 候选选择与锁定

选择一个原文有明确提取依据、参数和算法可落实的公开 PoR。前次报告中的 SW 是候选，不代表已完成实例化。先完成原文定理映射，再确定实现库和曲线；避免先选平台参数、后寻找能够迁就它的证明。

建议 `research/por_adapter_contract.md` 至少包含：

- 原文版本、算法编号、定理编号和使用的安全假设。
- KeyGen、Encode/Tag、Challenge、Prove、Verify、Extract、Decode 的输入输出。
- 公共参数、每文件状态、私有状态、标签和编码块的精确格式。
- 挑战索引是否有放回、系数域、随机分布和合法挑战空间。
- 接受率门槛、提取失败函数、查询数、时间和内存条件。
- extractor 是否公开、是否需要私钥、是否允许重置同一固定状态。
- 外层对象/组件身份和版本如何进入底层文件身份或认证状态。
- 原文支持的安全范围与本文需要的多组件、自适应更新范围之间的差距。

PDP 的不可伪造性证明不能替代 PoR 的 extractor。纠删码的直接恢复测试也不能替代从可接受响应中提取数据的论证。

### 7.2 先做底层微基准

单组件完成编码、打标签、挑战、验证、直接恢复和小规模 extractor 演示。记录挑战数变化时的证明字节、读取字节、验证时间及提取代价，用于更新阶段一的成本表。

微基准返回的 α 或性能数据只在其模型和环境内使用。密码学保证以定理为准，不能以测试若干次未伪造成功作为不可伪造性证据。

### 7.3 四组安全论证的具体任务

| 论证 | 要定义的事件 | 证明应解决什么 |
|---|---|---|
| 认证目标一致性 | 接受了不属于当前认证解析结果的组件或恢复关系 | 签名/哈希绑定、规范解析、条目数量与覆盖检查 |
| 底层响应正确性 | 接受违反底层合同的响应 | 明确归约到哪一个原语定理，不能靠外层根替代 |
| 当前对象组合提取 | 必要组件均满足前提，但组合恢复失败 | 启动顺序、各层状态认证、共享目标、提取时间和重建一致性 |
| 更新一致性 | 未授权旧版或混合版本被作为当前对象接受 | 授权、原子切换、局部身份及 nonce 不回退 |

组合提取证明先限定固定快照。为每个必要组件标出 εv、底层门槛和 δv；逐步说明外层 oracle 如何满足原始 extractor 的访问和挑战分布条件。只有这些成立后，才可使用分量失败概率的合并界。

尤其注意：对“整个闭包接受”的条件化可能改变某组件所见挑战分布；共享目标只生成一次证明也会改变接口。不能只说每个组件用了安全 PoR 就跳过归约。

### 7.4 如何处理非交互版本

若目标版本使用信标或哈希派生挑战，列出承诺时序、请求唯一性、重试规则、域分离、攻击者可选择输入及随机预言机条件。无法完成证明时，先提交已证明的交互版本，不把非交互版实验当作其自动安全扩展。

### 7.5 验收

证明稿中的每个 oracle、状态、概率和条件在算法中有对应实现；不存在靠未公开源文件、隐含可信目录或无法获得的私钥完成的“公开提取”。外层组合失败界和时间界具有统一、明确的适用范围。

## 8. 阶段五：完成最小端到端原型与更新

### 8.1 建议的目录结构

以下为后续实施建议，不表示已生成代码：

```text
Iot_Audit/
  research/          模型、主张账本、证明稿、文献对照
  prototype/
    formation/       精确代表/差分形成、加密、条带化
    por/             固定底层 adapter
    metadata/        M0—M3 目录与认证解析
    audit/           闭包、预算配置、挑战及验证
    update/          局部修改与当前根切换
    recovery/        提取、解码、对象重建
  experiments/
    configs/         可重放配置
    faults/          故障定义及注入脚本
    runners/         批量实验入口
    analysis/        统计与绘图
  artifacts/
    raw/             不覆盖的原始结果
    figures/         新版生成图
    manifests/       版本、数据与运行环境记录
```

### 8.2 实现顺序

1. 实现一份无损、确定性的对象形成与恢复，不加入审计，先验证原始记录精确重构。
2. 为每个组件接入固定 PoR，验证身份、参数和数据格式。
3. 实现认证目录和闭包解析，先走静态诚实路径。
4. 接入预算配置与规范挑战，对超预算和非法响应明确拒绝。
5. 加入故障注入、直接恢复与 extractor 模式，确保两者独立记录。
6. 实现普通记录更新，再做插入删除及页分裂，最后做代表变化。
7. 最后接入可选 BFT/信标部署与 coverage，分别测其额外成本。

### 8.3 关键更新用例

| 用例 | 预期检查 |
|---|---|
| 普通 DELTA 修改 | 修改业务条带及相关页/根；无关条带标签保持有效 |
| 插入/删除 | 更新记录计数、映射和范围；sid 不复用；必要时局部分裂 |
| REP 更新 | 全部相关 DELTA 重新验证精确恢复并按规则重构；不能计为普通单条局部更新 |
| 失败后重试 | 已使用 nonce 不重复消耗于不同加密输入；状态未部分激活 |
| 恢复旧内容 | 以新版本重新授权，不能回退加密计数或当前版本 |
| 并发更新 | 旧根冲突被发现；不能混合两个更新的页面和映射 |

相关验证应围绕安全不变量和真实失败路径。无需为文档或简单封装堆砌实现镜像测试。

## 9. 阶段六：实验矩阵、数据和结果记录

### 9.1 数据选择要求

选择具备时间、设备和数值测量字段的真实 IoT 数据，并确认使用许可及来源；再生成可控合成数据隔离代表共享度、条带布局和更新热点。数据集名称与下载路径在实施时核实，不提前假定当前可用。

形成参数与审计参数应固定或用独立调参集选择。最终评估使用留出的对象/时间窗口，避免只展示对本方案有利的形成结果。合成数据负责解释机制，真实数据负责说明目标负载是否存在。

### 9.2 参数扫描建议

| 维度 | 首轮应覆盖的情况 | 后续扩展 |
|---|---|---|
| 数据规模 | 可精确枚举的小对象、可运行的中等对象、接近目标使用规模的对象 | 不同设备数量和窗口长度 |
| 共享程度 | 无 DELTA、少量共享、中等共享、高度共享 | 真实数据形成后的分布 |
| 页容量 | 从少量条目到较大页，按几何间隔选候选 | 边界附近加密采样 |
| 预算 | 不可行、刚可行、一般、宽松 | proof/read/public 多预算前沿 |
| 故障 | REP、普通条带、META、页面、标签；单点与组合 | 固定针对性选择及持续变化故障分列 |
| 更新 | 普通修改、插入删除、代表变化；均匀与热点 | 批量更新、页分裂和连续版本 |
| 缓存 | 冷启动与热缓存 | 有限缓存及缓存失效 |

不要一次跑完所有维度的全组合。先用单因素或小规模组合定位机制，再选典型场景和边界做完整实验。

### 9.3 核心图表计划

| 图表 | 对应问题 | 必須包含 |
|---|---|---|
| 业务损失比例—漏检概率 | 第一项检测界是否准确 | 理论、模拟分开标记；A2 与 A4 |
| 预算—检测表现 | 优化是否有增量 | 同字节/读取预算；各策略独立调参 |
| r 与 REP 挑战强度配置图 | 为什么需要联合选择 | 共享证明的饱和区域与不可行区域 |
| 公共状态—更新成本—完整证明 | 第二项权衡 | M0—M3，动态 PoR 对照的证据类别 |
| 首次启动与热缓存成本 | 小公共入口是否转移开销 | 层数、往返轮次、字节和时间 |
| 故障—恢复结果表 | 审计是否对应业务恢复 | 检测、直接恢复、提取结果分别列 |

| 完整存储与计算分解 | 去重是否有净收益 | 一般压缩/无去重对照，所有辅助成本 |

### 9.4 必做攻击与错误路径

- 删除或隐藏验证状态，仍保留业务密文。
- 仅保留标签，删除对应编码块。
- 回放旧 file state、旧 REP、旧映射或旧对象头。
- 用另一对象或另一条带的有效证明替代目标证明。
- 返回合法成员证明，但遗漏必需条目或伪报计数。
- 提交范围重叠、重复 gid、错误页边界或错误长度。
- 更新只完成一半、超时、失败重试、并发旧根竞争。
- 损坏低于与高于编码恢复阈值，避免把检测与不可恢复混同。

### 9.5 原始结果格式

每条运行结果至少记录：协议配置版本、代码提交、数据哈希、方案/基线 ID、对象统计、页容量、挑战参数、故障定义、随机种子、环境、缓存模式、逻辑/物理读取、网络字节、耗时、峰值内存、拒绝原因、恢复记录数及根一致性。

确定性字节量精确统计；随机检测率报告试验数与二项比例置信区间；时间结果报告样本数和分布摘要。先通过预实验确定重复量，再固定主实验规则。零次漏检不等于漏检概率为零，也不能以少量试验验证密码学可忽略概率。

### 9.6 复现要求

提供一个小规模快速运行入口和一个论文规模配置入口。后者若运行时间长，应给出环境和预估资源。绘图必须从原始结果生成；理论曲线、模拟、底层微基准和端到端实测分别可追溯。旧 FastAudit/FullAudit 图不自动迁移到新协议。

## 15. 最小完整系统集与文献对照边界

仅做统计模拟不足以验证形成、认证、更新、故障与恢复之间是否一致；直接实现完整 pairing PoR、BFT、阈值信标和链上合约又会掩盖本研究最关键的依赖审计与元数据权衡。因此第一轮实现改为**四个共享底层、可端到端运行的最小完整系统**。它们不是对已有论文逐协议复刻，而是在统一数据、统一编码、统一认证审计后端和统一故障模型下，检验本文声称的结构增量。

### 15.1 统一工程边界

所有系统必须共享以下功能，避免通过给本方案额外能力或给基线额外负担制造结果：

| 层次 | 第一轮必须实现 | 明确不在第一轮声明的性质 |
|---|---|---|
| 数据形成 | 固定时间窗口、确定性 REP 选择、无损 DELTA/FALLBACK、规范序列化 | 相似分类算法创新或最优代表学习 |
| 机密性 | 可选 AEAD 加密、单调 nonce/version 记录、密钥由本地 Owner 模拟持有 | 公开验证隐藏明文的形成正确性 |
| 冗余与恢复 | 相同 RS 参数、擦除阈值、直接恢复和根重建 | 从任意高接受率 prover 得到的正式 PoR extractor 结论 |
| 完整性审计 | SHA-256 Merkle 认证、签名对象根、公开可验证的块/组件挑战 | 常数大小 pairing proof 或论文级公开 PoR 安全定理 |
| 存储端 | 本地 CSP 目录、组件版本、故障注入、拒绝和超时模拟 | 真实多节点拜占庭共识或云端物理 I/O 强制 |
| 更新 | 普通记录修改、原子根切换、旧根冲突检查、REP 更新的全依赖重构 | 高吞吐连续流的无阻塞 coverage |

第一轮审计后端命名为**认证纠删码组件审计**，而不是 PoR。每个挑战返回被请求编码块、Merkle 路径、组件/版本上下文和签名根绑定；验证端验证这些内容并统计真实字节。该实现能真实验证认证目标、网络成本、故障检测、直接恢复和更新一致性，但不能据此宣称实现了 Shacham--Waters 式紧凑公开 PoR 或 fixed-state extractor。后续 PoR adapter 只能替换同一后端接口，不能改变系统、基线和成本口径。

### 15.2 必做四个系统

| ID | 系统 | 对象与目录结构 | 审计策略 | 更新语义 | 它回答的问题 |
|---|---|---|---|---|---|
| S0 | Flat-EC-Audit | 将 REP、DELTA/FALLBACK、映射、META 规范序列化为一个对象；单一根和单一编码组件 | 均匀块挑战 | 任一记录修改重建整个对象 | 结构分解是否值得额外元数据与实现复杂度 |
| S1 | Component-FullDir | REP、普通条带、META 为独立组件；完整 Entry 目录公开可读 | 每轮固定 REP 挑战，加普通组件抽样 | 更新受影响组件和公开目录 | 依赖审计是否超出正确的认证目录加独立组件审计 |
| S2 | Component-RecursiveDir | 与 S1 相同业务组件；仅公开根目录状态，父页认证并提供子页验证输入 | 仍使用 S1 的固定 REP 加普通组件抽样 | 更新受影响叶页及根路径 | 小公共入口是否只是把启动和更新成本转移到递归访问 |
| S3 | Closure-Paged-Audit | REP、普通条带、META 与分页 Entry；公开 PageDescStore | 从记录抽样，认证解析 `D+(ell)`，对重复目标只验一次 | 仅更新受影响条带、页、META 与认证路径；REP 更新重构依赖 DELTA | 本文的依赖闭包审计和公开页描述符分页是否有实际适用区间 |

S1 必须是强基线，不能省略。S3 若只与 S0 或普通均匀抽样比较，不能说明闭包策略优于“每轮直接审计 REP”的简单有效方案。S2 只改变目录启动方式，审计策略保持 S1 不变；这样才能隔离第二项贡献。四者使用同一 REP/DELTA/FALLBACK 形成输出、相同 RS 参数、相同块大小、相同哈希/签名、相同故障集合和相同预算定义。

### 15.3 每个系统的最小端到端能力

所有 S0-S3 必须通过同一组操作，而不只是生成成本估算：

```text
build(records, policy) -> certified object
store(object) -> CSP local state
challenge(config, seed) -> request
prove(request) -> response
verify(response) -> pass/reject + exact cost
inject_fault(fault_spec) -> modified CSP state
recover(object_version) -> recovered encrypted components + root verdict
update(record_change) -> new certified version or atomic rejection
```

验收中每个系统均必须覆盖：诚实审计通过、REP 删除、普通条带删除、元数据页删除、低于/高于 RS 阈值的擦除、旧版响应、跨组件响应替换、更新中途失败和恢复后根不匹配。S0 没有页面时，对应页故障标记为“不适用”，但不因此少计其他故障与成本。

### 15.4 推荐的实现顺序

1. 先实现共同的 `formation`、`codec`、`merkle`、`storage`、`fault`、`recovery` 和 `metrics` 模块。
2. 实现 S0，作为完整序列化与全量更新的普通参照，不称为成本下界，也不代表动态 PoR 的最优实现。
3. 实现 S1，先完成正确的组件身份、目录解析和固定 REP 审计；这是第一项贡献必须面对的强基线。
4. 在 S1 的组件层上实现 S2，专门测冷启动、热缓存和目录路径更新。
5. 最后实现 S3；其形成和底层认证组件必须复用前述代码，只新增闭包解析、目标去重、分页描述符和局部更新差异。
6. 在四个系统均完成故障、恢复和普通更新后，才接入预算配置器；配置器不能提前依赖未实现的抽象成本。
7. 最后才评估真实 PoR adapter、BFT、信标和 coverage，并把新增成本作为单独层报告。

### 15.5 与现有论文的可比范围

本地审查已核对以下相邻工作。第一轮系统不应声称“复现”这些论文，除非逐项复现其密码算法、威胁模型、参数和运行环境；可做的是在可比维度上进行明确、受限的实验对照。

| 工作 | 可借鉴或可比较的维度 | 第一轮不能声称等价或覆盖的部分 |
|---|---|---|
| Gao et al. 2024，相似 IIoT 去重 | 真实 IoT 相似形成、REP/差分或相近表示的净存储、精确恢复 | 其 IIoT-Simhash、S-PoW 和安全去重协议的完整复现 |
| Liu et al. 2025，细粒度去重与完整性审计 | 去重映射、重构流程、存储与恢复辅助成本、细粒度故障场景 | 其 SSVT、重构矩阵、Bloom filter 和区块链协议性能复现 |
| Pan et al. 2026，动态去重与混合审计 | 更新触及组件、审计/更新开销分解、动态版本和去重审计边界 | 其混合审计公式、MHT 优化、所有权转移和链上实现复现 |
| Miao et al. 2024，共享数据审计与去重 | 认证器/密钥去重的辅助成本，以及共享数据批审计的相关工作定位 | 其共享用户、批量 pairing 验证和区块链机制复现 |
| Miao et al. 2025，相似数据可搜索审计 | 相似数据场景、认证索引和审计对象的定位差异 | 关键词搜索、trapdoor、仲裁和多副本可搜索审计复现 |
| Anthoine et al. 2021，动态 PoR | 动态单文件更新的强对照意义和时间/存储权衡口径 | 未实现该原语时，不得把 S0 的全量更新当成动态 PoR 的实测结果 |

论文中的对比表必须将结果分类为：`同机实测`、`本方案分析`、`文献报告`。不得把本文 S1/S2/S3 的测试数据画成对上述论文的直接性能柱状对比；只有在相同机器、参数、安全目标和实现层次均可核对时，才允许进行数值比较。

### 15.6 对论文贡献的重新约束

完成 S0-S3 后，可以得到三类有说服力的工程证据：

- S3 相对于 S1 的同预算业务损失检测、漏检和重复目标去重效果；
- S3 相对于 S1/S2 的公共状态、启动深度、完整通信和元数据更新权衡；
- S3 在形成、版本切换、故障、直接恢复和根重建中保持对象级一致性的端到端证据。

这些证据足以支撑“认证纠删码组件审计下的系统构造与实证评估”。在没有已证明并实际实现的公开 PoR adapter 前，论文必须把 fixed-state 可提取性保留为接口条件或后续扩展，不能把 Merkle 块挑战实验写成 PoR 提取定理的实证验证。

## 16. 原文复核后的执行修订

本节修订第 14—15 节过于刚性的前置条件。详细证据和实现规格见 [最小完整研究平台：论文核读与实施决策](./最小完整研究平台_论文核读与实施决策.md)。本次已使用技能 MinerU flash 解析并核读 Zotero 中 Gao 2024、Liu 2025、Pan 2026 的相关构造和实验章节；不是穷尽文献，也不是完整密码证明审核。公式 OCR 有明显失真，后续密码模块实现前须逐页视觉核验。

### 16.1 最低完整交付

交付一个共享代码平台的 S0、S1、S3、S2 四种配置，按这个顺序渐进实现，不开发四套独立服务器。先真实实现无损形成、AEAD/签名、RS、Merkle 块挑战、磁盘存储、认证目录、普通替换、故障和直接恢复；插入删除、分裂、完整 PoR extractor、BFT 和信标延后。原第 8 节 `prototype/` 为概念模块划分，实际 Python 实现统一使用第 14 节 `src/iot_audit/`，不要维护两份实现。

共同底座可与研究合同、精确模型和 PoR 合同核读并行，不要求先看到优势才允许写真实存储代码。G1 控制是否继续投入复杂密码/部署扩展，而不是禁止早期端到端验证。第 14.5 节是分批验收目标，不是“必须先完成 A4 才能开始预算配置”的循环前置条件。没有发现收益时报告负结果，不强制生成不存在的收益图。

### 16.2 控制变量与故障公平性

- 审计策略实验固定 Paged 布局，在相同预算下比较均匀条带、固定 REP+ordinary、闭包审计。必要 META/页保护统一计费。
- 目录实验固定审计策略及逻辑业务目标，比较 FullDir、单页、Paged、Recursive。不同布局的启动依赖按各自结构计量，冷热缓存分别报告。
- S3 对 S1 的整体比较同时改变两项机制，只能解释系统总差异；不能单独证明闭包策略优势。
- S0 不存在独立 REP 文件。跨布局故障使用声明的丢失字节预算或逻辑损坏映射，同时报告剩余冗余与实际恢复比例；不得把不同物理删除强度叫作相同故障。
- 整组件及其全部冗余丢失时，直接恢复应明确失败。RS 不能恢复不存在的全部输入；副本或跨组件编码必须额外设计并公平计费。

### 16.3 文献比较的实际工作量

首先实现 **R-Gao-Formation**：原文 IIoT-Simhash 与传统 Simhash 的分组比较，接入同一个无损编码后端，测形成和净存储。注明数值编码等适配假设；不称为 IIoT-SBSD 全协议复现，不拿用户所有权证明充当 CSP 持有审计。

第二候选是 **R-Pan-Core**：先核对公式，再复现单用户、固定版本的 Tag/Authenticator、Challenge、Prove/Verify，后做普通更新与 MHT。不先做交易、押金或链部署。更换群模型需要独立论证，原文历史安全参数和现代配置分列。

Liu 的重构矩阵、备份定位、TP 辅助重签、SSVT 与 Fabric 部署较多，首轮只做功能和恢复辅助成本对照，不承诺完整复现。普通精确去重加引用索引不是 BA-FGDIA。可搜索审计也不因题名含“相似”就必须纳入实现。

文献原报告、原文模块复现、适配后的结构基线、共同后端实测分别标记。同机运行仍不等于同安全目标；Merkle 逐块响应和紧凑 pairing 证明的性能不能直接用于宣称密码方案全面更优。接入真实 PoR 后必须重新配置预算并重跑关键实验。

### 16.4 最小运行与验收界面

Owner/Gateway、CSP、Verifier/恢复客户端至少以独立进程和分离目录运行，可用文件消息或本机 HTTP，无需多机或完整 Web UI。公共验证者不得访问源 CSV 或 Owner 私钥；恢复进程仅使用认证入口、必要密钥和 CSP 剩余数据；最终测试器独立比对原始记录。

拟建统一入口 `python -m iot_audit.cli`，支持 `build`、`upload`、`audit`、`fault`、`recover`、`update`、`compare`、`report` 子命令，统一接受配置和运行目录。这是接口目标，当前尚未实现；第 14.4 节示例也不是现成可运行命令。采用 src 布局时须提供 `pyproject.toml` 并先安装包。绘图入口统一到 `cli report`，避免目录与 `iot_audit.analysis.plot` 模块不一致。

最低演示序列：上传一个真实窗口 → 诚实审计 → 阈值内擦除 → 审计与恢复 → 修改普通记录 → 旧版响应拒绝 → 重启进程并恢复当前版本 → 删除全部 REP 编码分片并明确报告业务恢复失败。每一步留下真实消息、成本和根校验记录，不用预设检测概率代替验证。
