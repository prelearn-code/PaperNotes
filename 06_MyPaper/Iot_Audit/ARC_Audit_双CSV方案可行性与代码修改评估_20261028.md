# ARC-Audit 双 CSV 实验方案：可行性与代码修改评估

**评估日期：2026-10-28。** 评估对象是用户提供的[双 CSV 实验详细配置](<D:/local/download/ARC_Audit_双CSV三项贡献实验配置_20261028.md>)。本评估以 WSL 项目 `/home/zsw/codes/Paper/Exp/Iot_Audit_MY` 的实际源码和已保存的完整实验结果为依据。本文只评估方案并给出实施顺序；**尚未修改 WSL 代码、运行双 CSV 新实验或产生新性能结果**。旧论文、旧代码和旧结果应继续保留。

## 一、总体判断

**有条件可行，属于新归档格式与安全接口的系统重构，不是旧实验脚本的一次参数调整。** 两份 CSV 和已有的 AES-GCM、Ed25519、BLS 聚合、RS 修复、精确规范记录核验都能复用。必须重新设计的部分是跨文件稳定的 Base 表示、全局对象身份、共享页索引及其版本、跨批次审计闭包、跨快照恢复路由。新方案的 C1 存储收益和 Base 复用率**尚无实测证据**；应先做低成本的编码可行性与字节账本预试验，再投入五方法×三次构建和后续安全实验。

计划中“公开记录引用使 `K(i)=D(i)`”会改变当前论文的 C2 核心表述：现稿区分**公开充分闭包 K**与**授权精确闭包 D**。若公开 BaseID 和记录到 BaseID 的关系，公开验证者可以精确定位依赖，但也暴露跨记录/日期的等值关系。需要在新论文中明确将“公开精确定位”作为新的隐私与审计取舍，或保留私有引用版本作为另一完整方案；不能把两个版本的安全声明和旧实验数字混合。

| 关键条件 | 当前证据 | 可行性结论 |
|---|---|---|
| 两份 CSV 存在且规模符合旧报告 | WSL `database/hai21_raw/train1.csv` 为 **216,001 数据行**，train2 为 **226,801 数据行**（各加 1 个表头行）；现有正式运行清单中的 SHA-256 与当前 WSL 文件匹配 | 数据输入可用；新运行仍应记录实际哈希、列、时间范围和缺失值 |
| 固定 train1 分组能跨日直接编码 | **不能直接复用旧容器格式。** `container.encode()` 从当前批数据重算唯一 Base 数 `M` 和 `id_bits`，并要求等于当前 Model；旧 schema 的字段宽度、最小值、常量位也按日变化 | 先完成跨文件稳定编码合同和越界策略，再谈 BaseID 命中率 |
| 基础密码与恢复原语 | `secure_archive.py`、`secure_audit.py`、`secure_rs.py`、`secure_recovery.py` 已实现独立日归档上的 AEAD、签名、BLS、RS 与完整记录检查 | 可复用原语与测试思想；快照、对象身份、查找和路由接口需新版本 |
| FiDD/MPA/Miao 文献对照 | `secure_literature.py` 已有适配实现，但当前文献实验是旧日归档/独立目录和固定对象集合，不能原样用于新共享对象视图 | 可移植为补充基线；先核查审计语义、初始化和元数据计费 |
| 历史 Base 修复后再审计 | `ProtectedFetch` 能在请求内恢复密文并验证原始承诺；当前 `CloudStore` 没有持久恢复与再审计事务 | 定向测试可实现，但需独立写回/发布路径和故障注入副本 |

## 二、实际代码与数据核对

### 2.1 输入与既有正式结果

WSL 当前文件哈希：train1 `aa2f54a179015e279fe9623eefab0fe67ed74e3926657a93b355c290baa1d5cb`；train2 `3f8f4652fc8762a0f7d1478e5596565e54f4e3f8d0838bb709953caa0142e3ed`。这与旧[正式运行清单](ARC-Audit_Overleaf_Latest_Miao_20260930_222314/evidence/current-secure/config/full/run_manifest.json)记录的输入哈希相同。旧配置把 train1 分成 86,400/86,400/43,201 行三批，把 train2 分成 7,200/86,400/86,400/46,801 行四批；`experiment.py::day_windows` 要求时间严格递增且每秒连续，旧正式全量运行已通过该路径。

**不能直接沿用旧结果为新方案证据：** 旧 C1 是两个六小时窗口、4 方法×2 构建；旧 C2 是 54 个完整段请求；旧 C3 是 12,000 条故障观测加 480 条干净观测，均使用**每批独立 Base 和独立快照**。双 CSV 方案让 train2 引用 train1 共享页，因而物理对象集合、容量、故障总体、审计闭包和修复成功事件都变了。

### 2.2 首要技术阻碍：跨文件稳定的规范位串

训练窗口 `train1_2020-07-11` 前 21,600 行的 schema 与已保存的七个全量日批次逐字段比较如下。每项统计的分母是 79 个过程字段；“变化”仅说明旧日内规范布局不同，不等于记录值不可无损编码。

| 全量批次相对训练窗口 | 位宽变化 | FOR 最小值变化 | 常量状态变化 | 十进制小数位配置变化 |
|---|---:|---:|---:|---:|
| train1 07-11 | 16 | 36 | 0 | 1 |
| train1 07-12 | 24 | 45 | 2 | 7 |
| train1 07-13 | 20 | 49 | 2 | 2 |
| train2 07-31 | 33 | 50 | 7 | 11 |
| train2 08-01 | 29 | 48 | 6 | 4 |
| train2 08-02 | 23 | 46 | 2 | 9 |
| train2 08-03 | 18 | 47 | 2 | 0 |

旧 `sdaggd/container.py::encode` 对每批重新求不同 Base 的个数和局部 `id_bits`，然后把 Base 字典、引用流和偏差流写进**同一个日内容器**。`secure_archive.py::seal` 再把整容器切为 4,068 B 明文页加密，`base-catalog.bin` 当前还保存了该日 Base 明文位。因此“固定字段组/位位置＋把 BaseID 改成 HMAC”并不能得到新协议：train2 的数值坐标若仍由当日 FOR 最小值和位宽定义，相同 BaseID 的含义可能不同；若强用 train1 位宽，越界或常量变动会使编码失败或失真。

**建议先制定唯一的跨文件规范：** 对每个字段固定十进制量纲、整数映射、符号表示、位宽/越界码，固定字段顺序和分组版本，并在训练窗口以外做完整无损往返。训练只决定分组和 Base 位位置；新增数据落在旧范围之外时必须有可复核的逃逸编码或版本迁移，不能截断。固定宽度（例如规范有符号整数）实现最简单但可能损失压缩率，须与逃逸方案一起先做小规模存储预试验。`GroupID` 和 HMAC 输入必须绑定该规范版本、分组和位位置；同一 ID 不得跨不相容编码版本误判相等。

## 三、计划中需要修订的协议和公平性问题

1. **公开精确引用与保密性。** 公开 `RecordID→BaseID` 后，验证者可见同一 BaseID 被哪些记录和日期复用、引用频率与模式。这与旧论文“公开仅有充分闭包、精确引用需授权解密”的主张不同。应明确披露泄露函数与威胁模型，并比较“公开精确模式”和“私有引用模式”的完整成本/功能。`K(i)=D(i)` 只能在**新格式的物理密文页依赖**全部公开且受认证、其他隐藏依赖不存在时成立，不能从 Merkle 根相同直接推出。
2. **Merkle 结构不能只写“两个树根相等”。** 云不可信时，需要由拥有者签名/钉住版本根、树大小或键空间版本，并让每个查询的存在性证明绑定正确根。批次更新要有抗回滚的版本链或一致性证明；RFC 9162 的[签名树头与一致性证明](https://www.rfc-editor.org/rfc/rfc9162.html)可作实现参考，但不必照搬证书透明度协议。重复 BaseID 插入、旧根重放、两端分叉和更新中断都要明确处理。
3. **Base 打包与身份。** `BaseID→(PageID,Offset,Length,Digest)` 里的 Offset/Length 应明确是位还是字节、是否允许跨页；页应一经发布即不可改写，新增 Base 封入新页。否则追加新 Base 可能重写旧加密页，使旧 ID 指向的对象、标签和 parity 全部失效。HMAC 输入和 Merkle 叶子还需明确长度编码、域分离、规范版本和对象长度。
4. **审计密钥范围。** 旧 `seal()` 每批 `OwnerSecret.generate()`，不存在一把已部署的全局 BLS 审计密钥。最小可行实现是**每个密钥域各出一份证明，跨日合并对象读取和汇总通信**；若论文必须声称跨日一份聚合证明，应从 S1 起统一审计参数、完成密钥保管/轮换、对象身份绑定与跨批证明验证，旧标签不能直接拼接为一份新证明。
5. **C1 比较口径。** 新方案固定 train1 分组，而旧 Batch-SDA-GGD 每日重新学习分组，两者差别同时包含“冻结配置”和“跨文件共享”。建议除计划五个完整方案外，至少加一个**固定分组、但每批独立 Base**的诊断对照，隔离跨文件复用本身的收益。它是完整可运行方案，不需要把组件删除消融作为主图。要同时报告 S1 初始化成本、S2 增量成本和两文件累计成本；“本地不保存 Base 明文”也不能掩盖 HMAC 密钥、索引、缓存及历史密文读取成本。
6. **C2 文献方法。** FiDD/MPA/Miao 旧适配器按旧日快照和其自身目录工作，初始化、拥有者依赖目录和存储成本分列；它们没有自动得到相同的跨文件记录语义。主对照优先保持 **ARC-Public-Aggregate vs ARC-Public-Download** 的相同对象集合/权限配对，文献对照单列原生能力与适配成本，不能只给 90 个请求合计数就宣称所有方法等价。若更换 C2 主张，还应保留旧 Owner-MinRef 对照或说明为什么删去。
7. **C3 故障公平性。** 共享 Base 页可能服务大量 train2 记录，随机抽单目标和随机失效可能很少命中历史共享页。应预先分层报告“引用 train1 Base 的目标”“未引用历史 Base 的目标”“共享度高的 Base 页定向损坏”，同时保留不加选择的主随机故障集。对各方法固定**原始物理页损失**、按各自 parity 槽产生配对随机失效；对象数不同导致 `ceil(αN)` 不同，还应补做固定原片故障数或 Bernoulli 敏感性。恢复器不能从训练/未来 train2 目标得知 FrequencyD 排序。
8. **修复再审计的语义。** 当前 `ProtectedFetch` 只在内存中恢复并校验原密文承诺。定向“再审计”若要支持**持久修复**，必须将原对象同 ID、同字节恢复到故障注入副本，确认原签名清单、原标签和新读取仍通过；还要检查写回中断、修复后再次失效、parity 不足。不能把同一次请求缓存中的第二次认证叫作持久修复后的再审计。
9. **存储和通信账本。** 计划第 4 节 `S_total` 未明确签名、pin、Merkle 节点或证明缓存是否计云/本地；应以实际文件大小核对并分别列出。`HitRate` 分母应区分每批去重后的唯一 Base 查询和逐记录引用，且历史命中应注明“train1 历史”与“train2 前日新增”两类。计划使用 `max ciphertext 4096 B`，短页、公开目录与证明长度都必须按实际序列化字节计费。

## 四、建议的新版本实施顺序与退出门槛

在 WSL 新建独立 `sandbox/route_a_crossfile_v1` 和新 `results/route_a_crossfile_v1/<冻结运行名>`；只导入旧模块/原语，**不修改冻结的 `route_a_secure`、Plan63–65 和既有正式回执**。先保存输入哈希、配置、环境与源码清单，再逐阶段验收。

| 阶段 | 需要先实现/验证的内容 | 进入下一阶段的门槛 |
|---|---|---|
| 0：数据与稳定编码 | 固定字段坐标、训练分组、越界策略；对 train1 全量和 train2 全量做无损往返；测每日日内/历史 Base 不同 ID 与纯编码字节 | 任一输入不可逆、同值跨日 ID 不稳定、或需要未来 train2 信息才能定义分组时停止；先修规范 |
| 1：C1 轻量预试验 | 先在 1 个 train1 历史批次和 1 个 train2 批次做实际 Base 打包、HMAC、认证索引、密文页与标签；对 Batch-SDA-GGD 和固定分组独立 Base 做**同口径真实字节**比较 | 若完整安全累计成本不下降或下降仅来自改变编码/基线设置，先分析原因，不启动全量三贡献正式实验 |
| 2：全量 C1 | S1 初始化全 train1，S2 按日追加全 train2；新增页、索引根、目录、签名、标签、密钥/本地状态完整记账，三次构建作为运行波动而非独立数据集 | 各日根、BaseID 查询、无损记录、对象只上传一次和文件字节账本一致；公开/私有泄露合同冻结 |
| 3：C2 | 新跨快照审计规划器；同目标同页集合下 Aggregate/Download；攻击/回滚/跨根替换测试；文献适配先做可比性清单 | 合法跨文件目标通过；篡改拒绝；逐请求通信、证明、服务器读取及冷热初始化可复核 |
| 4：C3 | 新全局物理页 RS 侧车、跨快照认证恢复、无故障和分层随机/定向故障；持久修复后的新请求再审计 | 全部成功输出与规范源一致；失败不返回部分记录；历史页被保护并可真实修复；同 ID 写回后新请求验证通过 |
| 5：冻结正式实验与论文修订 | 固定故障种子、基线资格、统计单位、环境；输出逐请求回执、表/图及独立复核 | 只有这一版全链路结果才能替换主稿 C1/C2/C3 数字与贡献表述 |

**实验量提醒：** 计划中的 C2 `2×3×3×5=90` 是方法级请求数；C3 `5×3×50×4=3,000` 是四方法执行结果，对应的基础故障/目标单元只有 `5×3×50=750`，不能把 3,000 当独立样本。若把 train1 历史请求也放入 C3、重复三次构建或为所有文献方法重新建立物理对象，数量须在协议中重新推导。C3 主实验无读取硬上限虽然与旧稿一致，但后续 Plan64/65 已证明 512 KiB 临界退化可改变结论；建议至少同时报告 cold 512 KiB 与无限预算，避免新版论文的恢复贡献只在无限读取下成立。

## 五、论文层面的最终可行性判断

**工程可做，论文创新性有条件。** 双 CSV 历史 Base 复用加认证索引形成一个更连贯的系统问题，并把 C1 输出交给 C2/C3 使用，有潜力比三组各自构造数据的实验更有说服力。但“Merkle 树、HMAC BaseID、聚合审计、RS 修复”分别是已有部件；最终贡献须是**跨文件共享对象在认证索引下的统一存储、公开依赖审计和完整记录认证恢复合同**，并由真实空间、通信、故障与强基线结果支持。若 C1 完整安全成本没有改善，或公开精确引用带来的隐私泄露不能接受，方案应在轻量预试验阶段调整，而不是先运行全部正式实验。
