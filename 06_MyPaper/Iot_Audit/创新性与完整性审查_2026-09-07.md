# Iot_Audit 初稿创新性与完整性审查

审查日期：2026-09-07。主要对象：`paper_cn.md`；`核心方案2.md` 和 `pic/` 用于核对旧方案与实验材料的对应关系。本报告不修改论文原稿。

**结论：选题有继续研究的价值，但当前稿件尚不足以支撑一篇优质的完整研究论文，尤其尚未达到稿中所指向的 TDSC 系统论文的完成度。主要障碍不是创新点数量少，而是核心增量尚未与强组合基线拉开距离，安全证明存在接口与量词缺口，现有实验材料也没有验证当前协议。** 这不是“已被某篇论文完全做过”的结论；本次检索未发现与整个方案逐项相同的工作，但这种未发现不能作为首创性证明。

## 1. 目前真正有价值的研究问题

论文抓住了一个合理问题：删除很小的共享代表可能使大量差分记录无法重构，因此按存储字节均匀抽样，不一定符合业务恢复风险。把记录映射、被挑战条带、代表依赖、公开验证状态和当前版本放在同一认证解释下，也比单纯给数据附加一组标签更完整。

当前稿主动区分在线审计、调度覆盖和固定状态提取，承认 Gateway 的形成信任、公开参数可用性和原始 SW 模型边界，这些都是应保留的严谨性。不能为了显得贡献更强，再把 `CoveragePass` 写成完整恢复保证。

不过，固定状态黑盒提取、可信初始化本身并不是缺陷；很多 PoR 理论本来就在类似模型下成立。真正需要回答的是：**在相同信任和资源条件下，你的机制相对于认证目录加标准 PoR，额外证明了什么，或者节省了什么？**

| 稿中贡献 | 现有支撑 | 创新增量判断 |
|---|---|---|
| 星形依赖对象、Impact/RecoveryLoss | 对象模型、业务例子、损失定义 | 有价值的任务建模；损失计数本身较直接，不能单独承担主要理论贡献 |
| RecordBinding 派生 LINK/REP-LINK | 认证解析链与上下文检查 | 是必要设计，但强基线也可以照此实现；还需说明为何超出正确使用认证数据结构 |
| 分页元数据启动与公开状态认证 | PageDescStore、AuditEntryRoot、META-first 提取 | 是当前最有希望的系统贡献；必须证明其在公共状态、证明和更新成本上的收益 |
| 同一快照的组件提取与对象根重建 | 定理 6、附录 H | 合理的组合方向；目前主要依赖“每个组件均可提取”再逐项组合，非平凡性仍不足 |
| 无放回覆盖 | Fisher–Yates、SwapMap、coupon collector 比较 | 适合作为调度优化和消融项，不宜承担密码学创新 |
| 原子更新、CSMS、suite 注册、BFT 生命周期 | 多个定理及状态规范 | 大多是支撑机制；定理数量不等于独立创新数量 |

## 3. 阻碍投稿的主要问题

### 3.1 “扁平 PoR 不足”的论证过强，容易被强基线击穿

位置：摘要、引言第 25 行附近，II.D。

如果把当前对象的代表、差分、映射、必要恢复元数据和规范解码规则一起序列化，并由外部可信根确定版本，标准 PoR 恢复完整字节串后，原则上可以解析并重构对象。它未必满足你的局部更新和差异化冗余效率要求，但不能直接说它在功能上无法保证对象恢复。

引言正文已经承认可以恢复扁平字节串，这一点与摘要的绝对措辞不够一致。应改成：**直接整体 PoR 能实现恢复目标，但是否能在局部更新、风险分配和公开状态开销之间取得合适代价，需要进一步设计。**

映射 A 配证明 B 的反例只能击败“没有检查映射与挑战目标一致性”的弱组合。一个签名目录把 gid、版本和 native file id 绑定后，再据此生成挑战，就能排除这类直接错绑。新方案应与这种正确组合比较。

### 3.2 组合恢复定理合理，但当前创新含量有限

位置：VII.E 定理 6、附录 H。

前提已要求 META、REP、全部页面和全部 ordinary stripes 都满足各自提取条件；结论通过顺序调用 extractor、解码及根校验得到。这不是逻辑循环，也不是因为“条件性”就不成立，但很容易被审稿人认为是直接的逐组件组合和联合界。

建议明确提出认证依赖图的可启动性条件：哪些公开状态必须外置，哪些可通过已恢复节点获得，何时出现无法启动的环，以及如何完整枚举必要节点。证明一般性的充分条件，再说明星形业务图加元数据依赖图为何满足它。只有在确实能够证明时才提升为“必要条件”或下界。

另一条可行路线是以系统贡献为主：证明该分层实现在公共持久状态、更新放大、证明通信上的明确权衡，并通过强基线实验支撑。无需为了数量继续增加安全谓词。

### 3.3 SW 的上下文适配不能仅靠 Part-One soundness 推出

位置：VII.C 定理 2、附录 F.1、附录 J.3。

原 SW Theorem 4.2 约束的是接受响应必须等于诚实计算的聚合值。你的 CTX 游戏却把“在未获得目标 prover state 时产生任意目标有效证明”作为获胜事件。即使敌手输出了正确的目标聚合值，它也赢得你的游戏，却没有违反 SW 的响应正确性结论。因此目前这一步引用并未完成归约。

这表示**证明缺口，不是已经得到 SW 伪造攻击**。应补一个明确的目标上下文认证器不可伪造归约，说明源认证器、公开目标 file tag、非目标查询和随机预言机如何模拟；或者重构外层真正需要的游戏，基于正确响应/目标数据可提取性组合，避免提出额外且未经证明的合同。

另外，F.1 在 KeyGen/Preprocess 之前让敌手提交完整 ctx，但 ctx 又包含生成后的 PublicAuditStateDigest。应分开“预先承诺的逻辑目标”和“初始化后产生的密码上下文”，定义合法目标如何派生。

附录 J 的 SW 提取阈值与交互复杂度公式与本次核读的原文 Theorem 4.3 对应；公开验证不需要提取私钥也有原文依据。问题主要在新游戏的适配，不宜把这一部分全部判为错误。[SW 原文，Theorems 4.2–4.3](https://hovav.net/ucsd/dist/verstore.pdf)。

### 3.4 选择性目标安全与自适应多轮结论之间缺少桥梁

位置：VII.A Game RCS、VII.C 推论 1、附录 G.4。

正文说底层只证明选择性两上下文安全，却又给出自适应多轮 operational soundness。对 epoch、slot 和域位置乘一个联合界，只解决攻击发生在哪一次的问题，不能自动解决如何在底层初始化前承诺尚未确定的目标上下文。

此外，真实 CSP 初始获得所有存储组件的 prover state，而 F.1 禁止获得目标 PSt。必须说明真实攻击怎样映射到这个受限游戏，不能直接把两者等同。

修订可选：把结论收紧为预先固定目标上下文下的多轮安全；或给出自适应、多文件、可更新游戏及完整归约。若试图通过猜测目标对象创建查询解决，应写清查询顺序、模拟和对应损失。

### 3.5 nonce 的版本规则有可构造的复用路径

位置：IV.B.4，第 427 行附近。

稿件规定明文 payload 改变时递增 payload_ver；位置、类型或依赖改变时递增 binding_ver。但 nonce 仅由记录密钥与 payload_ver 派生，而 AEAD 的 AD 含依赖上下文。

例如采用数值差分：原代表为 10，记录为 11，delta 为 1；更新代表为 20、记录为 21，delta 仍为 1。代表承诺改变，AD 改变，并要求重新加密全部 DELTA；但按现有增量条件，delta 明文没变，payload_ver 未必增加，于是同一记录密钥下复用 nonce。

对一般 nonce-based AEAD，这不满足唯一性使用条件。应引入独立 encryption_ver：任何需要重新加密且明文或 AD 改变的操作都消耗新版本，版本在失败重试、并发更新和回滚时也不得复用；完全相同的幂等重试重用已生成密文。96 位截断 KDF 也仅提供概率抗碰撞，不能写成数学上的绝对唯一，可采用有界计数编码或给出碰撞预算。这里是协议规格缺口，实际影响还取决于最终选择的 AEAD。[RFC 5116，Section 2.1](https://datatracker.ietf.org/doc/html/rfc5116#section-2.1)。

### 3.6 PageDescStore 解决的是有代价的启动问题

位置：IV.B.5、VIII.C。

本稿把所有当前页面的完整公开验证状态保存在共识层，确实避免从尚未恢复的页面里寻找验证该页的参数。但这意味着启动依赖转移到必须可读的共识状态，公共状态为 O(P_meta)，并非仅一个常数大小根。

需要与“把所有 ordinary 描述符/file tags 都放在公共目录”的简单基线比较。你的价值可能是把 O(number of stripes) 的公共 file states 降为页面级状态，代价是页面内 opening、分页更新和额外页面 PoR；这个权衡必须量化。还应比较合并 Manifest 和 AuditStatePage 的实现，解释分开两套页面究竟节省什么。五层结构各有当前职责，并不等于五层都是不可替代的。

### 3.7 无放回覆盖会与动态更新争用

位置：VI.F、VI.I、VIII.C。

AUDITING 期间禁止数据更新，紧急更新必须 AbortEpoch，新版本 coverage 从零开始。这保证单 epoch 的版本一致，却不能保证持续写入的 IoT 对象最终完成 coverage。它不是对定理 5 的反例，而是业务活性缺口。

必须报告写入速率变化下的完整覆盖成功率、审计延迟、写阻塞和中止浪费。如果目标是封闭窗口/微批次归档对象，应直接限定应用范围；如果目标是持续可变对象，需解决快照审计或增量覆盖的版本语义。

还要统一单位：稿中有“m_cov 个 slot 完成覆盖”，配置中又有 c_cov=2。应明确 slot 是单个 ordinal 还是包含多个 ordinal 的链上轮次，避免轮数、信标次数和验证成本相差倍数。

### 3.8 当前实验材料不能直接证明当前方案

位置：VIII.F、IX；`核心方案2.md`；`pic/svg/fig_exp4_audit_mode_tradeoff.svg`。

第 VIII 节是“应当报告什么”的评估设计，没有当前协议的完整实测结果。目录确实已有图，SVG 包含 FastAudit/FullAudit 标签；旧核心方案使用统一 AuditMHT 和 BN254 链上聚合验证。当前稿则是分页启动、逐域 RPDP、VerifierModule、PageDescStore 和 fixed-state 组合恢复，且仅给出 SW-Sym-Theory 候选。

所以不是“完全没有做过实验”，而是**尚未建立旧实验与当前协议之间的可验证对应关系**。当前目录未见支撑这版协议的实验代码、原始测量和配置。不能把旧 FullAudit gas 或 proof size 直接当成新版开销；应附协议版本、代码提交、测试参数和逐字段成本账本。

现代 Type-3 实例不是所有理论论文的必要条件，也不要求必须找到一篇替你完成所有适配的已有论文；你可以自己提供独立正确证明。但若选择系统论文路线，就必须有能实际运行且安全论证对应的实例。

## 4. 其他需要收紧的表述与规范

- **REP-LINK 的边际作用。** 协议同时有 critical REP 域和每条 delta 的 REP-LINK。在唯一代表对象中，需说明一个当前 REP proof 加上全部已认证依赖检查是否足够。独立域 proof 可能增加抽样强度，但那也可以通过同预算增大一次 REP challenge 实现；必须做相同预算消融。
- **审计与恢复连接。** 不能把一轮或一次 coverage 当成每组件 epsilon 下界。若要增加统计保证，必须规定固定 prover 状态、独立挑战和置信度，并对全部组件控制同时置信误差；该结论不能搬到任意跨轮自适应变化的 CSP 上。
- **Reset 的随机性。** SW 原文使用干净 scratch tape 和新的 randomness tape。本文“完整机器状态重置”应明确固定持久状态、如何处理 prover 新随机币，以及随机预言机是固定函数还是只固定已查询表，避免无意中改变导入定理的接受概率空间。
- **状态层次。** ObjectHeader 含 lifecycle_status，但生命周期又由独立 state_ver 改变。需写清 Header 字段是形成时状态还是实时状态，进入 AUDITING/FROZEN 是否需要 Gateway 重签。当前多处“版本/状态一致”不足以唯一决定实现。
- **调用者归责。** SubmitAuditProof 的最终规范需在标记 FAILED 之前验证提交者确为当前 CSP 或有其签名授权，否则第三人提交坏 proof 可能触发冻结。现有叙述“CSP 提交”不能替代显式入口检查；这属于待补检查，尚未复现实际代码漏洞。
- **分页局部性。** 明确 next-fit 只用于初始化，还是更新时也重打包；若条目增长导致后续页面级联移动，“对应常数页更新”的边界会改变。给出溢出、分裂、合并及元数据字节上限规则。
- **信标预测时点。** 应定义在任何合格成员尚未能组合阈值份额之前不可预测，及各方获得份额和 CSP deadline 的关系；唯一签名防同输入重抽样，不自动提供所有参与者同时获知随机数。

这些问题可以修复，但说明文稿目前更接近详细研究规格，而不是已经完成证明与实现闭环的方案。

## 5. 能支撑优质论文的重构路线

建议保持主题，收敛成三个彼此关联的贡献，不再堆更多注册模块和状态名。

**贡献一：以业务记录恢复为目标的依赖审计模型。** 保留共享代表损失放大，但需要从模型导出有意义的设计或界限：在相同 proof 字节/服务器读取预算下，依赖感知审计如何改变损失检测概率、检测时间或可恢复记录比例。若只是 Impact 的定义，贡献仍偏薄。

**贡献二：带明确公共状态预算的可启动认证元数据构造。** 把“不能循环依赖验证状态”形式化；比较公共全目录、单层元数据、分页分层三种方案，并给出公共状态—证明大小—更新放大的量化权衡。当前最值得做实的是这一项。

**贡献三：一个完整实例与端到端验证。** 完成真实安全游戏和 adapter，给出从对象形成、更新、审计、破坏注入到恢复的可复现实验。无放回调度、BFT 和 CSMS 作为这一实例的组成部分即可。

理论路线也可以成立，但需要比当前逐组件联合界更有解释力的通用结果；系统路线则必须证明代价和收益。当前稿停在两条路线之间：理论很长但增量不够突出，系统细节很多但尚无对应实测。

## 6. 必须采用的强基线与最小实验闭环

| 基线 | 如何构造 | 回答的问题 |
|---|---|---|
| 完整对象序列化＋标准 PoR | 包含全部必要映射/恢复材料，外部绑定当前版本 | 你的结构分解是否在更新与成本上必要 |
| 认证目录＋独立条带 PoR | 目录派生真实 challenge，REP 每轮审计，文件状态公开可读 | LINK 与依赖保护是否超出正确组合的自然能力 |
| 公共全描述符目录 vs 分页目录 | 相同底层 primitive、参数、对象布局 | 分页节省的公共状态是否抵得过 opening 与更新代价 |
| 动态 PoR＋规范对象表示 | 明确选用方案支持的公开/私有验证及信任差异 | “整体方案必然全量重编码”是否成立，局部更新增量有多大 |
| StrongRandomAudit | 保留所有其他机制，只改有放回抽样 | 仅隔离 coverage；它是消融基线，不能验证整篇论文的全部创新 |

至少完成下列实验，每项均报告相同安全目标和预算，并区分实测、分析和模拟：

1. **真实 IoT 数据的净存储收益。** 同时计入 REP/DELTA/FALLBACK、RS、AEAD、标签、索引、页面、认证树和共识状态；比较普通压缩及精确去重，报告代表集中度和 fallback 比例。只报告 payload 压缩率不够。
2. **相关损坏与恢复。** 删除 REP、删除差分页、删除元数据页、混合旧版本、错误映射；测量检测时间、漏检概率和实际可恢复记录数，区分整条带删除与阈值以内擦除。
3. **关键消融。** 去掉 REP-LINK 但保留 critical REP、合并元数据页、取消分页、覆盖改为有放回；保持挑战预算一致。弱错绑实现可用于解释反例，不作为主性能对手。
4. **并发更新。** 普通修改、插入删除、REP 变化、suite 迁移、不同写入速率；报告触及条带/页面数、重编码字节、coverage 中止率和写入延迟。
5. **端到端开销。** Gateway 预处理、CSP 证明、完整 ProofBody、每个 BFT 节点验证、共识写状态和 finality；旧版 gas 与新版原生 verifier 成本分开。
6. **恢复与提取分别验证。** 工程恢复测真实下载/擦除解码；理论 extractor 模拟测独立挑战、线性秩增长、恢复坐标和根重建。禁止把模拟器直接读取保存的全部原数据计为黑盒提取成功。

不必先做大规模完整平台。应先实现“认证目录＋独立 PoR”的强基线和一个可工作的当前实例；若在相同预算下难以展示增益，先调整研究贡献，再投入区块链平台工程。

## 7. 修改优先级与最终判断

| 优先级 | 必须完成的事 | 完成标志 |
