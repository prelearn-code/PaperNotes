# 三个贡献的紧凑实验结果分析

日期：2026-09-22。判断对象：当前实现和本轮合成小规模实验，不评价尚未执行的正式矩阵，也不重新裁定参考文献的新颖性。

## 1. 判断

当前证据不足以支撑“三项独立贡献均成立”的论文叙事。系统已有可运行、可检验的基础，值得继续研究；但 C1 的组合贡献需要安全定义和真正的角色隔离，C2 更适合作为覆盖保持引理及实现优化，C3 需要先修正强基线公平性和局部更新实现，再裁决是否具有独立贡献。

验证结论：**Needs revision（比较性论文结论需要修订）**。原始运行记录可用来描述这版实现的小规模行为；不能把 `complete` 或 `validation.json: valid` 解释成 v2.0 的 G0/G1/G2 全部通过。

| 贡献 | 本轮证据 | 当前判断 |
|---|---|---|
| C1 状态绑定的搜索—位置—共享内容审计 | 诚实和已有攻击检查通过；认证组合可运行；JOINT 的匹配消融收益较小且受传输时延影响 | 支持系统可执行性，未建立独立创新或性能贡献 |
| C2 覆盖保持的重复感知聚合 | 自然负载相对 POS-FOLD-NZ 收益约 0.009% / 0.161%；受控 q/u 的收益大多在几个百分点内 | 不支持独立高性能贡献；建议保留覆盖/分布理论并合并到 C1 |
| C3 授权增量状态迁移 | 相对现有 LOCAL-MERKLE 更新降低 11.60% / 13.00%；但该基线额外签名，其他局部后端也共用变化集路径 | 有工程信号，公平性与机制独立性未建立；不能据此宣称新算法优势 |

唯一数据源：[本轮结果目录](../../../Exp/Search_Audit/results/feasibility_unlimited_20260922_173610)。未混入停止的旧长任务、失败试跑或历史 pilot。

独立复算代码：[assess_feasibility_results.py](../../../Exp/Search_Audit/scripts/assess_feasibility_results.py)。输出：[recomputed_evidence.json](../../../Exp/Search_Audit/results/feasibility_unlimited_20260922_173610/analysis/recomputed_evidence.json)。运行方式：

时间收益统一为 `1 - 本方案时间 / 基线时间`。先在相同分布、种子、配置内取时间中位数，再计算配对收益，最后取种子收益中位数。它不等于两列总体中位数的比值。三种子 bootstrap 区间仅供探索；单种子探索点不作显著性结论；小样本 p95 不作正式尾延迟验收。

## 3. C1：功能可执行，性能和隔离证据尚不足

默认 ROOT-HLA+Merkle 主点查询时间（八段计时之和的种子中位数，再取三种子中位数）为均匀 179.19 ms、偏斜 126.84 ms。这是当前实现及 TCP relay 路径的测量，不是纯密码计算时间。

JOINT 对匹配 SEP-OPT 的配对结果：

| 分布 / 后端 | 查询中位数收益 | 总应用消息字节收益 |
|---|---:|---:|
| 均匀 / Merkle | 1.26% | 0.35% |
| 偏斜 / Merkle | 3.50% | 0.37% |
| 均匀 / PCS | 2.36% | 0.43% |
| 偏斜 / PCS | 1.03% | 0.45% |

JOINT 相比 SEP-OPT 每条响应少 96 字节，仅占总消息约 0.35%–0.45%，不接近预注册 20% 通信目标。均匀 PCS 的三个种子时间收益范围为 −20.20% 至 +2.46%，不支持稳定加速。不能用 ROOT-HLA 与自己等价的直接组合制造竞争曲线。

需要修正两个实验边界：

1. [c1_experiments.rs](../../../Exp/Search_Audit/src/bin/c1_experiments.rs) 的 proving/verifying 在父进程运行；[c1_wire_relay.rs](../../../Exp/Search_Audit/src/bin/c1_wire_relay.rs) 子进程仅解码、重新编码和回传消息。当前实现证明了消息可跨进程传输，尚未满足 Owner/Server/Verifier 独立执行的 M01 合同。沙箱保护 relay 不能替代 Server/Verifier 本身的隔离。
2. 阶段时间存在约 40–42 ms 的台阶。例如偏斜 ROOT-HLA+Merkle 的 seed-0 搜索 prove 中位数 41.02 ms，而 seed-1 为 0.21 ms；部分挑战阶段反向出现约 42 ms。客户端开启 TCP_NODELAY，relay 端未开启且分两次写长度和正文。TCP 延迟 ACK/Nagle 交互是待验证原因，不能仅凭代码就确认因果。应做双方 NODELAY/合并写的小对照，并分离本地计算与消息往返时间。

现有 query 总时间还没有包括 owner_start 阶段，应用消息字节也不是 TCP/IP 实际线上字节。论文需准确标明计量范围。C1 默认定位应是组合安全问题与完整协议；创新需由威胁模型、绑定性质与归约支持，而不是依赖这里的百分比。

## 4. C2：相对优化折叠强基线，优势很小

[自然负载配对统计](../../../Exp/Search_Audit/results/feasibility_unlimited_20260922_173610/statistics/primary/paired_comparisons.csv)：

| 分布 | UNIQUE-NZ 相对 POS-FOLD-NZ 核心收益 | 三种子 bootstrap 95% 区间 |
|---|---:|---:|
| 均匀 | 0.0088% | −1.7037% ～ +0.6373% |
| 偏斜 | 0.1607% | −1.7510% ～ +1.0219% |

区间跨零，未观察到稳定的自然负载优势。受控 q=256 的关键点如下；此处列种子配对收益中位数，不将种子极值称为置信区间：

| q/u | 均匀标签下，相对 POS-FOLD-NZ | 偏斜标签下，相对 POS-FOLD-NZ | 相对 POS-RAW（两标签约值） |
|---|---:|---:|---:|
| 4 | 1.59% | 0.41% | 32.6%–32.7% |
| 8 | 2.25% | 0.36% | 44.9%–45.2% |
| 16 | 0.68% | 0.70% | 53.1%–53.5% |

POS-RAW 的显著差距表明重复折叠本身有价值，不能据此证明 UNIQUE-NZ 比已经优化的折叠算法具有显著优势。

受控程序使用 `position % unique` 生成均衡重复布局；两种分布标签影响负载生成，但这里没有真正独立的偏斜重复度布局。因此不能声称已经完成“均衡/偏斜受控映射”双实验。C1 当前只使用 UNIQUE-NZ，缺少三策略在相同完整查询中的配对运行，也没跑 D=0.75 自然点。本轮不能裁决集成查询 ≥10% 目标，但现有核心结果没有积极性能信号。

建议将 C2 表述为“在固定逻辑样本及认证映射后保持覆盖与系数分布的简化聚合”，以证明和计数说明价值；暂不将其列为独立高性能创新。

## 5. C3：测得收益，但关键强基线存在设计混杂

| 分布 | 本方案更新中位数 | LOCAL-MERKLE 更新中位数 | 配对收益 | 探索性区间 |
|---|---:|---:|---:|---:|
| 均匀 | 34.74 ms | 39.22 ms | 11.60% | 10.68%–12.67% |
| 偏斜 | 34.70 ms | 39.03 ms | 13.00% | 10.91%–15.09% |

这些收益低于 20% 目标。对 LOCAL-MERKLE 的配对 p95 收益约 53.7%/55.5%，但它同样受下述额外授权检查影响。单种子探索点更新收益约 11.46%–13.30%，只说明当前实现下趋势延续。固定位置审计查询约 34 ms；均匀查询中位数回退约 0.12%，偏斜收益约 1.99%。这里的“查询”只审计目标文件首/中/末位置，不是完整关键词搜索查询。

公平性问题直接见 [c3.rs](../../../Exp/Search_Audit/src/c3.rs) 的 `prepare_update`、`apply_update`：所有变体已经验证完整补丁的统一签名，LOCAL-MERKLE 还对“相同完整消息 + 组件索引”附加签名，并逐个验签。其他变体没有这些附加签名，但共用 `validate_delta_patch`、局部更新和状态字典更新。

均匀 seed-0 的实测授权 pairing_checks：LOCAL-MERKLE 平均每次 5.5，AUTHORIZED-DELTA-MERKLE 为 1；平均页读/页写二者均为 1/1.09，状态哈希计数相同。说明差异很大程度可能来自授权层额外开销，而非不同局部更新算法。尚无证据证明这些附加签名是强局部基线满足同一功能合同所必需的；因此现有 12%–13% 不足以证明独立算法优势。

其他对照也支持这一谨慎解释：本方案对 FULL-REBUILD 更新收益仅约 0.40%/0.64%，对 LOCAL-PCS-NOPRE 仅约 1.10%/3.40%。对 NOPRE 查询收益约 19.23%/20.86%，但此对照同时换了 Merkle/PCS 后端，不能全部归功于授权变化集。

还有四个实现/计量限制：

- `delta_snapshot` 克隆被更新文件，`apply_delta_patch` 克隆整条引用向量，`validate_delta_patch` 扫描保留位置计算字节数；尚未满足“工作严格限于变化集及路径”的要求。页计数局部不等于全部 CPU/内存工作局部。
- [c3_wal.rs](../../../Exp/Search_Audit/src/c3_wal.rs) 的 checkpoint 保存全部历史事务，恢复先从原输入重建，再重放历史。WAL 清零不能证明持久化总空间有界，也不能证明恢复成本与历史长度无关。
- prepare+apply 计时包含提交路径，但末尾 checkpoint 在其外；终点 100 次审计只记录第 1/10/100 次，完整轨迹总成本不能从现有逐阶段行数完整重建。组 wall time 混有 Oracle、构建和攻击测试，也不能直接充当纯业务成本。
- storage.csv 只列出部分存储分项，没有完整索引、秩树、运行内存及所有元数据字节；不足以验收“辅助空间增加≤20%”。LAZY 终点仍可有 pending log，不能默认为全部后台成本已支付。

C3 应首先回答：去掉不必要的重复授权后，相同局部后端上，新的统一迁移协议究竟比普通安全组合新增了什么性质或节省了什么必需工作？如果答案最终是相同协议，就应合并配置，不保留两条人为区分的曲线。

## 6. 下一步的优先级

1. **先修正比较有效性**：将冗余逐组件签名明确列为消融；建立功能匹配、没有重复工作且允许批验签的强局部基线。冻结两者算法差异和信任边界后再测。
2. **修正 C1 测量与执行边界**：短对照定位 40 ms 时延；分离计算/传输，并让角色子进程真正执行各自计算。现有数值保留为旧版诊断证据。
3. **聚焦 C3 局部性与持久化**：消除不必要的全文件引用克隆/扫描；明确字节 splice 的不可避免重分块成本；设计真实状态快照和截断重放；计入 checkpoint、终点剩余维护及完整空间。
4. **重新组织论文**：C1 作为组合安全框架候选主贡献，C2 作为其覆盖保持性质，C3 作为候选动态扩展。完成公平对照后，再决定是否足以保留 C3 为第二项独立贡献。
5. **随后才扩样**：先在一个主点复核修正效果，再补少量尺度点和缺失的 C2 完整查询对照。不要先花数周扩大有混杂的现有矩阵。

本轮分析未改动核心算法或原始实验结果，未启动新实验。仅新增原始结果复算脚本、复算证据与本文。下一轮实现应另建结果目录，避免将修正前后数据合并成同一组。
